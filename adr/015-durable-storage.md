## Durable storage · `sec:storage:record`

**Decision (Database)** · `dec:storage:postgresql` PostgreSQL is the durable store. The implementation tracks the latest published PostgreSQL beta release, with the same deliberate forward-tracking stance as (`dec:toolchain:compiler`). The storage gate records the actual server version and tests that supported beta; a stable server or mock is not an unnoticed substitute. Dependency review owns changes to the beta surface. Before 1.0, rebuild stores rather than migrate across project versions under (`rule:compatibility:pre-one`).

**Rule (Connection configuration)** · `rule:storage:configuration` The storage library's complete connection configuration is JSON and contains only the PostgreSQL connection details needed to reach and authenticate to the instance, including transport security parameters where required. Every other implementation setting, rule, declaration and durable fact belongs in the database or the public inputs, including the separate public startup tuple of (`amend:api:listener-bootstrap`). The entire configuration is instance-private material, including host, port, user, password and transport-security parameters, not merely its credentials. Keep the file and referenced private material outside tracked files with restricted access. For the designed executable, acquire its private connection metadata and role password once from the supervisor credential directory under (`amend:observe:supervisor-entry`), and assemble that complete configuration only inside protected storage. The generated password is separately sealed and delivered under (`rule:observe:credential-store-contract`); no administrator assembly of a plaintext password JSON file is required. An arbitrary path, environment value or command argument is not an alternate secret entry. The existing library file reader is evidence of its own boundary, not of supervisor delivery. Read it directly into secret-owned storage and parse into a secret-owned configuration aggregate under (`dec:observe:secrets`), (`inv:observe:secret-boundary`); expose it only at the connection call that needs it. Observation records its secret role and type marker, and records public queries, parameters, results and driver errors in full without sanitization under (`rule:observe:privacy`). The driver must preserve secret typing through its retained configuration and error paths before unsanitized errors are admissible. The file must not become a second policy store; absence of a required database declaration is a refusal, not an implicit local default. The read-only first node retains the password-based login of (`amend:storage:host-secured-login`) even on a local socket: peer identity is not an admitted fallback. Its runtime configuration contains its own password; the separate schema-owner configuration goes only to the bootstrap task under (`amend:storage:runtime-roles`). Both come from the durable first-start set of (`dec:observe:first-start-route`), with external role provisioning reconciled before use. The administrator applies only its client-derived restricted verifier; no plaintext role password reaches the server. The derivation, custody, descriptor wiring and evidence are (`rule:observe:credential-store-contract`) and (`verif:observe:credential-bootstrap`), not a new runtime statement or public provisioning API. No new database credential is generated on an ordinary reconnect or restart.

**Amendment (Trusted PostgreSQL service)** · `amend:storage:server-trust` PostgreSQL is a trusted component of the deployment: the storage library takes its catalogue, query and diagnostic results as correct under the server’s contract. Frames between the shim and server travel only over the admitted host-secured path under (`case:intranet:host-secured`) and (`amend:storage:transport-evidence-boundary`); that path admission excludes a third party placing frames on the channel, independently of trust in the server. Secret reachability and credentials remain in secret-owned carriers by construction under (`rule:storage:configuration`), (`dec:observe:secrets`) and (`inv:observe:secret-boundary`); all network data outside those instance-private carriers is public. The library carries no speculative handling of a server that violates that contract. An actually observed server defect, including a diagnostic that carries a secret, is a PostgreSQL bug to report upstream and handle on its evidence. Library conformance is exercised against the real supported service under (`gate:storage:evidence`). Checking an existing schema or index definition validates deployment state returned by that trusted service; it does not claim to verify the server implementation.

**Model (Effective history)** · `model:storage:scd2` Versioned rules, declarations and facts use slowly changing dimension type 2 history. A logical version row has a stable key, immutable payload, effective opening boundary and exclusive closing boundary, with an open end for the current terminal version. A change closes its predecessor and opens its successor at the same boundary. To avoid updating historical bytes in place, the durable representation appends an immutable closure fact naming the predecessor and appends the successor in one transaction; the row's effective end is resolved from that closure. No historical payload or opening boundary is overwritten, and closures cannot be rewritten. This is the durable form of (`model:design:declarations`), not permission to migrate between pre-1.0 representations (`rule:compatibility:pre-one`).

**Invariant (Total history)** · `inv:storage:intervals` For each key and its declared lifetime, effective intervals are half-open, ordered and partition that lifetime: there is exactly one row at every admitted boundary, no overlap and no gap. Before creation a key is absent; withdrawal is an explicit absence-valued successor, not a hole in history. A successor starts strictly after its predecessor's opening boundary, and a predecessor has at most one closure. Competing writers serialize succession so they cannot fork the current row. Announcement and effective boundaries remain distinct, and the paper's lead and admissibility rules still govern which successor may be committed.

**Rule (Historical resolution)** · `rule:storage:as-of` An act, boundary or epoch resolves every applicable declaration at its own authoritative effective boundary in a consistent database snapshot, never by the newest row. Resolution returns the effective version identities with the values; zero or multiple rows for a required live key is a storage-contract failure. A later-effective rule never changes an earlier verdict. After stable adoption, a running system can receive new rule rows at their announced effective boundary without rewriting history; before 1.0 this behavior is exercised by tests, not relied on for compatibility across releases (`rule:compatibility:pre-one`).

**Invariant (Atomic succession)** · `inv:storage:atomicity` Closing a predecessor and opening its successor commit together or neither commits. Accepted acts, debit evidence and admitted epoch results are durably committed with the references needed to explain them; a partially written result is never visible as admitted. Rollback, interruption and concurrent writers cannot expose a gap, duplicate current version or result bound to a mixed declaration snapshot. Derived indexes and caches can be rebuilt from the durable evidence and public inputs without changing their meaning.

**Convention (Ownership)** · `conv:storage:ownership` The deployment operates the PostgreSQL instance: availability, backups, recovery operations, access control and credential custody remain its responsibility. The implementation owns the schema, history model, transactional storage contract and historical resolution. This clarifies persistence operations in (`conv:vision:operations`) without making an operational availability claim. Database possession never supplies a hidden mathematical cause: binding inputs and their effective declarations remain publicly reproducible. On a rebuild under (`rule:compatibility:pre-one`), public inputs restore public history; the deployment re-supplies instance-private connection and operating settings through the secret bootstrap of (`rule:storage:configuration`) and (`inv:observe:secret-boundary`), including private settings that normally reside in database rows. The connection JSON remains connection-only; subsequent secret-owned settings enter through the authorized bootstrap, not an additional policy file.

**Gate (Storage evidence)** · `gate:storage:evidence` From the bite introducing storage, the repository gate runs storage tests against a real instance of the supported PostgreSQL beta and records its server version. Tests exercise exact as-of boundaries, explicit withdrawal, refusal of overlapping or gapped histories, atomic close/open with rollback and interruption, conflicting writers, and an earlier verdict unchanged by a later-effective rule. A missing or unsupported instance fails the storage gate rather than skipping it. This record provisions nothing and claims no such test already executed; the implementation placement and bite obligation are (`proposal:design:storage-placement`) and (`verif:design:storage-history`).

**Amendment (Private configuration)** · `amend:storage:secret-configuration` (`rule:storage:configuration`) adopts the secret-type boundary of (`amend:observe:full-content`) for the complete connection configuration. Protecting only the password leaves private reachability and operating details exposed; protecting the whole value at acquisition avoids a drifting list of log exclusions. JSON remains connection-only, the file remains access-restricted and untracked, and public historical data is observed in full. No storage implementation or driver conformance is established by this amendment.

**Amendment (Shared storage conformance)** · `amend:storage:conformance` The functional in-memory store and real PostgreSQL adapter run the same storage-contract suite under (`rule:harness:conformance`), with implementation identity in every result. Fast mock runs are explicit partial evidence; (`gate:storage:evidence`) still requires the supported real PostgreSQL beta, plus service-specific concurrency, durability and restart cases. Missing real service results cannot be replaced by mock success. This adds a proven fast substitute without weakening the historical or atomicity contract (`rule:harness:real-services`).

**Amendment (Private bootstrap ownership)** · `amend:storage:rebuild-ownership` (`conv:storage:ownership`) assigns re-supply of instance-private settings to the deployment during a forward-only rebuild (`amend:compatibility:private-bootstrap`). Historical public evidence and private operational custody have different sources, so neither an unavailable private setting nor possession of a database can stand in for the other.

**Amendment (Immutable marker policy)** · `amend:storage:marker-settlement` The public declaration and epoch-reference obligations of (`model:storage:scd2`), (`rule:storage:as-of`) and (`inv:storage:atomicity`) include the fixed pre-genesis marker policy, its identity and edition, recognized marker lineage and interpretation, the marker policy-selected accepted-set representation and verification evidence under (`model:design:storage-history`). Persist the complete lists or uniquely verifiable public openings needed to recover every accepted member and verify the policy and both acceptance bounds; a bare commitment is not sufficient durable evidence. A successor declaration cannot reinterpret a recognized marker or erase predecessor acceptance; a different marker policy does not replace the old one within its sequence. Commit an admitted result and its common marker snapshot together. Each settled snapshot retains the exact chain-prefix height and block hash fixed by (`rule:design:marker-recognition`), the immutable buffer, and the linked-chain evidence through that height plus the buffer. An event-pinning floor is not this epoch prefix. Reconstruct the prefix from the marker's unique disclosed inclusion location, validate its buffered successors, and compare the retained pair exactly; unavailable or contradictory evidence prevents settlement rather than selecting the current tip. This retention duty governs the revised store: its settled-prefix carrier is (`amend:design:epoch-authentication-restoration`) and its package-chunk retention is (`amend:storage:publication-evidence-retention`), both prerequisites of the revised representation's PostgreSQL re-admission. The first read-only store admits no settled epoch. It holds an admitted result rebuilt from declared public inputs under (`amend:storage:admitted-rebuild`), with fixture premises disclosed, not a result settled on a chain; no test chain exists for that instance. Its version-one binding/marker-prefix succession checks remain required but do not establish chain settlement. Retaining a settled prefix beside a version-one package in a separate relation is set aside because it would be a host-only attachment outside restored admission and complete-content equality. Extend (`gate:storage:evidence`) with as-of marker-evidence retention from bite 2 and atomic ledger/package references in the later slices; a consistent SQL snapshot alone does not establish the realization's marker contract (`rule:design:marker-recognition`). This preserves the history model while making the new package causes explicit.

**Amendment (Unsettled recognition persistence)** · `amend:storage:unsettled-recognition` (`amend:storage:marker-settlement`) distinguishes recognition from settlement under (`rule:design:marker-recognition`). A stored recognition is an unsettled SCD2 row keyed by history identity, policy identity and edition, verifier profile, burn publication edition and sample convention, retaining the disclosed candidate positions, complete recognized prefix and first refusal. Supersession appends closure and successor facts under (`model:storage:scd2`); it never overwrites historical evidence. A candidate refusal need not terminate the prefix under first-valid selection. The host implementer must supply finality evidence under the published assumptions at the published settlement depth in bite 8 before any marker becomes settled evidence. Sampled amounts are persisted only as their burn publication, never as the settled burn map that (`alg:design:burn-snapshot`) derives in bite 5. Recognition alone authorizes neither a settled storage row nor a snapshot claim. This observer-time succession remains separate from admitted result ancestry: it describes later disclosures under one observer key, not the parent relation of a result. The result-qualified observations of (`amend:storage:admitted-correspondence`) retain the exact disclosure used by each node under distinct keys and editions. Closing or superseding an observer-time recognition neither deletes a side branch nor redirects a retained result's reference. Applying observer recency to choose a result branch is set aside because recognition is not deployment selection or settlement authority.

**Amendment (Supported prerelease)** · `amend:storage:next-major-prerelease` (`dec:storage:postgresql`), (`gate:storage:evidence`) and (`amend:storage:conformance`) use the newest published pre-release of the next PostgreSQL major line, including a release candidate later than that line’s betas. **Decision (Secret-terminating PostgreSQL integration)** · `dec:storage:secret-shim` Beside (`dec:storage:postgresql`), choose a secret-terminating shim in front of pinned, unmodified tokio-postgres 0.7.18 as the first storage route. The shim owns TLS, real startup and SCRAM-SHA-256 in secret-owned state; the driver uses connect_raw with NoTls, TLS disabled and a public placeholder identity over the shim’s in-process stream. The shim answers that placeholder startup locally with AuthenticationOk and public startup state, removes session_authorization ParameterStatus messages, substitutes BackendKeyData and keeps the real cancellation capability secret-owned; subsequent frames retain these boundaries. It owns cancellation. This preserves upstream query, transaction and type handling with less new protocol code than a minimal client and less permanent patch maintenance than a driver fork. A minimal own client is rejected because reimplementing query recovery, statements and transactions adds protocol risk without improving secrecy. This is a route choice, not settlement of (`open:design:secret-integrations`): persistence remains disabled until (`rule:storage:first-commit-evidence`) passes and receives independent review.

**Rule (Shim fallback)** · `rule:storage:shim-fallback` Under (`dec:storage:secret-shim`), the secret-aware driver fork is a fallback only on executed evidence that the pinned driver cannot operate over the placeholder in-process stream, or requires a filtered message that cannot be represented publicly without breaking its contract. Record the failing criterion and witness before switching. A fallback must have a vendoring rule and provenance, archive-checksum hash-citation family, licence notices, record 005’s vendoring amendment, record 001’s ownership adoption, name-specific discipline exceptions, registered upstream tests and clean restricted-text scans. No fallback is admitted by this decision. The TLS secrecy hold applies to either route; a TLS incompatibility alone does not prove either driver criterion.

**Rule (Storage dependency pins)** · `rule:storage:dependency-pins` Every dependency admitted for (`dec:storage:secret-shim`) has an exact version, reviewed features, licence and archive checksum resolvable through a registered hash-citation family, with all transitive resolutions reviewed and locked. A version move repeats that review. **Amendment (TLS and SCRAM evaluation)** · `amend:storage:tls-evaluation` (`dec:storage:secret-shim`) names rustls 0.23.46 with tokio-rustls 0.26.6 as the preferred TLS adaptation target, not an admitted unmodified transport. **Amendment (Storage login choice)** · `amend:storage:host-secured-login` (`dec:storage:secret-shim`) accepts only SCRAM-SHA-256 from secret-owned password, transcript and derived-key material over an admitted host-secured path. Refuse cleartext, MD5, GSS, SSPI, Kerberos and every other authentication request with a bounded cause; AuthenticationOk before verification of the SCRAM server signature also refuses. Peer authentication removes the password and state machine but is Unix-socket-only, couples roles to operating-system identity and authenticates a forwarded socket’s connecting account. SCRAM costs a secret-owned state machine and the bounded primitive residue in (`amend:storage:scram-residue`), but works over sockets, loopback, tunnels and backbones and proves that the server holds the verifier. Its server proof does not protect the post-login path: (`case:intranet:host-secured`) still assigns that duty to the operator. No alternate authentication or trust fallback is admitted. **Amendment (Authentication and frame bounds)** · `amend:storage:transport-bounds` (`amend:storage:host-secured-login`) accepts SCRAM iteration counts from 4,096 through 100,000 inclusive. PostgreSQL's default of 4,096 is the minimum: an impostor cannot choose a cheaper proof for an offline password search than that baseline; the upper bound limits unauthenticated work. This is a floor, not a claim that the default meets every deployment's password policy. The printable-ASCII password profile remains; malformed attributes, a non-extending nonce, a missing mechanism, a server error instead of the offer and both iteration bounds refuse before a client proof. Storage's record shapes must fit the one-MiB payload bound per protocol frame; oversize frames refuse without truncation. Relay buffers are sized to their frame, each frame is submitted in one write_all, and TCP uses TCP_NODELAY. Elapsed throughput is warning evidence, never a correctness oracle.
