## Durable storage · `sec:storage:record`

**Decision (Database)** · `dec:storage:postgresql` PostgreSQL is the durable store. The implementation tracks the latest published PostgreSQL beta release, with the same deliberate forward-tracking stance as (`dec:toolchain:compiler`). The storage gate records the actual server version and tests that supported beta; a stable server or mock is not an unnoticed substitute. Dependency review owns changes to the beta surface. Before 1.0, rebuild stores rather than migrate across project versions under (`rule:compatibility:pre-one`).

**Rule (Connection configuration)** · `rule:storage:configuration` The configuration file is JSON and contains only the PostgreSQL connection details needed to reach and authenticate to the instance, including transport security parameters where required. Every other implementation setting, rule, declaration and durable fact belongs in the database or the public inputs. The entire configuration is instance-private material, including host, port, user, password and transport-security parameters, not merely its credentials. Keep the file and referenced private material outside tracked files with restricted access. Read it directly into secret-owned storage and parse into a secret-owned configuration aggregate under (`dec:observe:secrets`), (`inv:observe:secret-boundary`); expose it only at the connection call that needs it. Observation records its secret role and type marker, and records public queries, parameters, results and driver errors in full without sanitization under (`rule:observe:privacy`). The driver must preserve secret typing through its retained configuration and error paths before unsanitized errors are admissible. The file must not become a second policy store; absence of a required database declaration is a refusal, not an implicit local default.

**Amendment (Trusted PostgreSQL service)** · `amend:storage:server-trust` PostgreSQL is a trusted component of the deployment: the storage library takes its catalogue, query and diagnostic results as correct under the server’s contract. Frames between the shim and server travel only over the admitted host-secured path under (`case:intranet:host-secured`) and (`amend:storage:transport-evidence-boundary`); that path admission excludes a third party placing frames on the channel, independently of trust in the server. Secret reachability and credentials remain in secret-owned carriers by construction under (`rule:storage:configuration`), (`dec:observe:secrets`) and (`inv:observe:secret-boundary`); all network data outside those instance-private carriers is public. The library carries no speculative handling of a server that violates that contract. An actually observed server defect, including a diagnostic that carries a secret, is a PostgreSQL bug to report upstream and handle on its evidence. Library conformance is exercised against the real supported service under (`gate:storage:evidence`). Checking an existing schema or index definition validates deployment state returned by that trusted service; it does not claim to verify the server implementation.

**Model (Effective history)** · `model:storage:scd2` Versioned rules, declarations and facts use slowly changing dimension type 2 history. A logical version row has a stable key, immutable payload, effective opening boundary and exclusive closing boundary, with an open end for the current terminal version. A change closes its predecessor and opens its successor at the same boundary. To avoid updating historical bytes in place, the durable representation appends an immutable closure fact naming the predecessor and appends the successor in one transaction; the row's effective end is resolved from that closure. No historical payload or opening boundary is overwritten, and closures cannot be rewritten. This is the durable form of (`model:design:declarations`), not permission to migrate between pre-1.0 representations (`rule:compatibility:pre-one`).

**Invariant (Total history)** · `inv:storage:intervals` For each key and its declared lifetime, effective intervals are half-open, ordered and partition that lifetime: there is exactly one row at every admitted boundary, no overlap and no gap. Before creation a key is absent; withdrawal is an explicit absence-valued successor, not a hole in history. A successor starts strictly after its predecessor's opening boundary, and a predecessor has at most one closure. Competing writers serialize succession so they cannot fork the current row. Announcement and effective boundaries remain distinct, and the paper's lead and admissibility rules still govern which successor may be committed.

**Rule (Historical resolution)** · `rule:storage:as-of` An act, boundary or epoch resolves every applicable declaration at its own authoritative effective boundary in a consistent database snapshot, never by the newest row. Resolution returns the effective version identities with the values; zero or multiple rows for a required live key is a storage-contract failure. A later-effective rule never changes an earlier verdict. After stable adoption, a running system can receive new rule rows at their announced effective boundary without rewriting history; before 1.0 this behavior is exercised by tests, not relied on for compatibility across releases (`rule:compatibility:pre-one`).

**Invariant (Atomic succession)** · `inv:storage:atomicity` Closing a predecessor and opening its successor commit together or neither commits. Accepted acts, debit evidence and admitted epoch results are durably committed with the references needed to explain them; a partially written result is never visible as admitted. Rollback, interruption and concurrent writers cannot expose a gap, duplicate current version or result bound to a mixed declaration snapshot. Derived indexes and caches can be rebuilt from the durable evidence and public inputs without changing their meaning.

**Convention (Ownership)** · `conv:storage:ownership` The deployment operates the PostgreSQL instance: availability, backups, recovery operations, access control and credential custody remain its responsibility. The implementation owns the schema, history model, transactional storage contract and historical resolution. This clarifies persistence operations in (`conv:vision:operations`) without making an operational availability claim. Database possession never supplies a hidden mathematical cause: binding inputs and their effective declarations remain publicly reproducible. On a rebuild under (`rule:compatibility:pre-one`), public inputs restore public history; the deployment re-supplies instance-private connection and operating settings through the secret bootstrap of (`rule:storage:configuration`) and (`inv:observe:secret-boundary`), including private settings that normally reside in database rows. The connection JSON remains connection-only; subsequent secret-owned settings enter through the authorized bootstrap, not an additional policy file.

**Gate (Storage evidence)** · `gate:storage:evidence` From the bite introducing storage, the repository gate runs storage tests against a real instance of the supported PostgreSQL beta and records its server version. Tests exercise exact as-of boundaries, explicit withdrawal, refusal of overlapping or gapped histories, atomic close/open with rollback and interruption, conflicting writers, and an earlier verdict unchanged by a later-effective rule. A missing or unsupported instance fails the storage gate rather than skipping it. This record provisions nothing and claims no such test already executed; the implementation placement and bite obligation are (`proposal:design:storage-placement`) and (`verif:design:storage-history`).

**Amendment (Private configuration)** · `amend:storage:secret-configuration` (`rule:storage:configuration`) adopts the secret-type boundary of (`amend:observe:full-content`) for the complete connection configuration. Protecting only the password leaves private reachability and operating details exposed; protecting the whole value at acquisition avoids a drifting list of log exclusions. JSON remains connection-only, the file remains access-restricted and untracked, and public historical data is observed in full. No storage implementation or driver conformance is established by this amendment.

**Amendment (Shared storage conformance)** · `amend:storage:conformance` The functional in-memory store and real PostgreSQL adapter run the same storage-contract suite under (`rule:harness:conformance`), with implementation identity in every result. Fast mock runs are explicit partial evidence; (`gate:storage:evidence`) still requires the supported real PostgreSQL beta, plus service-specific concurrency, durability and restart cases. Missing real service results cannot be replaced by mock success. This adds a proven fast substitute without weakening the historical or atomicity contract (`rule:harness:real-services`).

**Amendment (Private bootstrap ownership)** · `amend:storage:rebuild-ownership` (`conv:storage:ownership`) assigns re-supply of instance-private settings to the deployment during a forward-only rebuild (`amend:compatibility:private-bootstrap`). Historical public evidence and private operational custody have different sources, so neither an unavailable private setting nor possession of a database can stand in for the other.

**Amendment (Immutable marker policy)** · `amend:storage:marker-settlement` The public declaration and epoch-reference obligations of (`model:storage:scd2`), (`rule:storage:as-of`) and (`inv:storage:atomicity`) include the fixed pre-genesis marker policy, its identity and edition, recognized marker lineage and interpretation, the marker policy-selected accepted-set representation and verification evidence under (`model:design:storage-history`). Persist the complete lists or uniquely verifiable public openings needed to recover every accepted member and verify the policy and both acceptance bounds; a bare commitment is not sufficient durable evidence. A successor declaration cannot reinterpret a recognized marker or erase predecessor acceptance; a different marker policy does not replace the old one within its sequence. Commit an admitted result and its common marker snapshot together. Extend (`gate:storage:evidence`) with as-of marker-evidence retention from bite 2 and atomic ledger/package references in the later slices; a consistent SQL snapshot alone does not establish the realization's marker contract (`rule:design:marker-recognition`). This preserves the history model while making the new package causes explicit.

**Amendment (Unsettled recognition persistence)** · `amend:storage:unsettled-recognition` (`amend:storage:marker-settlement`) distinguishes recognition from settlement under (`rule:design:marker-recognition`). A stored recognition is an unsettled SCD2 row keyed by history identity, policy identity and edition, verifier profile, burn publication edition and sample convention, retaining the disclosed candidate positions, complete recognized prefix and first refusal. Supersession appends closure and successor facts under (`model:storage:scd2`); it never overwrites historical evidence. A candidate refusal need not terminate the prefix under first-valid selection. The host implementer must supply finality evidence under the published assumptions at the published settlement depth in bite 8 before any marker becomes settled evidence. Sampled amounts are persisted only as their burn publication, never as the settled burn map that (`alg:design:burn-snapshot`) derives in bite 5. Recognition alone authorizes neither a settled storage row nor a snapshot claim.

**Amendment (Supported prerelease)** · `amend:storage:next-major-prerelease` (`dec:storage:postgresql`), (`gate:storage:evidence`) and (`amend:storage:conformance`) use the newest published pre-release of the next PostgreSQL major line, including a release candidate later than that line’s betas. The supported target at this decision is PostgreSQL 19 RC 1. The storage gate records the actual server version and refuses an absent or different version under (`verif:design:storage-history`); neither a stable release nor a mock silently substitutes. Dependency review owns advancing this target. This supersedes the beta-only wording while retaining deliberate forward tracking and forward-only store rebuilds.

**Decision (Secret-terminating PostgreSQL integration)** · `dec:storage:secret-shim` Beside (`dec:storage:postgresql`), choose a secret-terminating shim in front of pinned, unmodified tokio-postgres 0.7.18 as the first storage route. The shim owns TLS, real startup and SCRAM-SHA-256 in secret-owned state; the driver uses connect_raw with NoTls, TLS disabled and a public placeholder identity over the shim’s in-process stream. The shim answers that placeholder startup locally with AuthenticationOk and public startup state, removes session_authorization ParameterStatus messages, substitutes BackendKeyData and keeps the real cancellation capability secret-owned; subsequent frames retain these boundaries. It owns cancellation. This preserves upstream query, transaction and type handling with less new protocol code than a minimal client and less permanent patch maintenance than a driver fork. A minimal own client is rejected because reimplementing query recovery, statements and transactions adds protocol risk without improving secrecy. This is a route choice, not settlement of (`open:design:secret-integrations`): persistence remains disabled until (`rule:storage:first-commit-evidence`) passes and receives independent review.

**Rule (Shim fallback)** · `rule:storage:shim-fallback` Under (`dec:storage:secret-shim`), the secret-aware driver fork is a fallback only on executed evidence that the pinned driver cannot operate over the placeholder in-process stream, or requires a filtered message that cannot be represented publicly without breaking its contract. Record the failing criterion and witness before switching. A fallback must have a vendoring rule and provenance, archive-checksum hash-citation family, licence notices, record 005’s vendoring amendment, record 001’s ownership adoption, name-specific discipline exceptions, registered upstream tests and clean restricted-text scans. No fallback is admitted by this decision. The TLS secrecy hold applies to either route; a TLS incompatibility alone does not prove either driver criterion.

**Rule (Storage dependency pins)** · `rule:storage:dependency-pins` Every dependency admitted for (`dec:storage:secret-shim`) has an exact version, reviewed features, licence and archive checksum resolvable through a registered hash-citation family, with all transitive resolutions reviewed and locked. A version move repeats that review. Any digest introduced by the storage slice must separately pass (`gate:identity:implementation`), including its identity-class admission and permanent recipe; archive provenance is not an exemption for new semantic identities. No dependency, checksum family or new digest is admitted by this route decision alone.

**Amendment (TLS and SCRAM evaluation)** · `amend:storage:tls-evaluation` (`dec:storage:secret-shim`) names rustls 0.23.46 with tokio-rustls 0.26.6 as the preferred TLS adaptation target, not an admitted unmodified transport. Source review finds ordinary owned server names in handshake and session state, ordinary trust anchors and client-certificate chains, and a name-mismatch error containing the expected name; tokio-rustls retains the connection and propagates its error through io::Error. OpenSSL 0.10.81 and native-tls 0.2.18 do not remove the hold: native TLS state retains names and certificates and its diagnostic stack has printable data. A conforming typed integration or an independently authorized narrow TLS adaptation must eliminate these copies and error paths before configuration; merely wrapping or scrubbing them is forbidden by (`inv:observe:secret-boundary`). postgres-protocol 0.6.12’s SASL state copies the normalized password into an ordinary vector and is unsuitable for real private authentication. The shim must instead keep password, transcript, derived keys and error data secret-owned, use reviewed HMAC-SHA-256 and PBKDF2 primitives with explicitly reviewed temporary-state lifetimes, and implement SCRAM-SHA-256 and its channel-binding variant with either secret-preserving SASLprep or a stated password restriction. Owner: the storage implementer and independent integration reviewer. TLS and SCRAM implementation admission remains held on the evidence below; no production transport is enabled here.

**Rule (First storage commit evidence)** · `rule:storage:first-commit-evidence` Before enabling persistence under (`dec:storage:secret-shim`), the storage implementer supplies all eight items to the independent integration reviewer: (1) acquisition reads the configuration file directly into a secret carrier and parses there, with no intermediate ordinary String, generic JSON value or parser error retaining private bytes, demonstrated by compile-time probes and sentinel parser failures; (2) after successful connection, Debug of every retained configuration, client, connection, cancellation token, parameter map and shim or fork object contains no private sentinel, alongside a reviewed retained-state data flow; (3) real PostgreSQL 19 RC 1 runs use distinct sentinels for user, password, database, host alias, port, TLS server name and paths, capturing every observation stream, error Debug, Display and full source chain and panic across success, wrong password, unknown role, unknown database, refused port, unreachable host, required TLS refusal, TLS name mismatch, unknown CA, server closure during authentication, cancellation, mid-query drop and connection loss; (4) each leakage witness fails because it finds a sentinel, not because compilation fails, when the unmodified driver receives private configuration directly; (5) a positive witness records public queries, parameters, results and SQL errors in full without sanitization; (6) protocol witnesses cover SCRAM-SHA-256 with and without channel binding, recorded server version 19 RC 1, every storage statement shape through the extended protocol, commit, rollback, serialization failure and cancellation through the secret-owning path; (7) representative post-authentication errors and notices for those statements are checked for sentinels, and any diagnostic capable of echoing private content is constructed as typed private data inside the secret-owning boundary before reaching an ordinary driver error, never scrubbed, while public diagnostics remain fully recorded; (8) exact dependency pins, resolvable archive checksums, licence notices, restricted-text scans of new or vendored text and (`gate:identity:implementation`) for every new digest complete provenance. (`open:design:secret-integrations`) records its driver part as settled only after all items pass; a source review or chosen route alone does not settle it.

**Amendment (Host-intranet storage route)** · `amend:storage:host-intranet` Under (`rec:intranet:decision`) and (`case:intranet:host-secured`), the shim of (`dec:storage:secret-shim`) opens a Unix-domain socket or TCP connection to the host-provided endpoint itself, using secret-owned reachability, and performs real startup and authentication. The driver still sees only its public placeholder identity and the shim's in-process stream; ParameterStatus filtering, BackendKeyData substitution, secret-owned cancellation and the fallback criteria of (`rule:storage:shim-fallback`) remain required. TLS leaves this first route: the TLS component, certificate and server-name secrecy work in (`amend:storage:tls-evaluation`) belong to (`open:intranet:guarded-transport`), not to first-route admission. The SCRAM secrecy work remains required. This supersedes the first-route TLS duties in the decision, fallback rule and evaluation without admitting the shim or enabling persistence. The public store-link case declaration of (`inv:intranet:explicit-case`) is a separate bootstrap setting, available before database access; it does not enter or change the wholly private connection JSON of (`rule:storage:configuration`).

**Amendment (Storage login choice)** · `amend:storage:host-secured-login` (`dec:storage:secret-shim`) accepts only SCRAM-SHA-256 from secret-owned password, transcript and derived-key material over an admitted host-secured path. Refuse cleartext, MD5, GSS, SSPI, Kerberos and every other authentication request with a bounded cause; AuthenticationOk before verification of the SCRAM server signature also refuses. Peer authentication removes the password and state machine but is Unix-socket-only, couples roles to operating-system identity and authenticates a forwarded socket’s connecting account. SCRAM costs a secret-owned state machine and the bounded primitive residue in (`amend:storage:scram-residue`), but works over sockets, loopback, tunnels and backbones and proves that the server holds the verifier. Its server proof does not protect the post-login path: (`case:intranet:host-secured`) still assigns that duty to the operator. No alternate authentication or trust fallback is admitted. The first route restricts passwords to printable ASCII, avoiding an unreviewed SASLprep allocation; other password profiles require separate admission.

**Amendment (Host-secured first-commit evidence)** · `amend:storage:host-secured-evidence` (`rule:storage:first-commit-evidence`) retains eight items, interpreted for (`amend:storage:host-intranet`) as follows. **Amendment (PostgreSQL token exception)** · `amend:storage:token-exception` (`dec:intranet:signed-tokens`) does not replace PostgreSQL's protocol-fixed login. **Amendment (SCRAM primitive residue)** · `amend:storage:scram-residue` Under (`amend:storage:host-secured-login`), the accepted bounded residue is the padded key block local to hmac 0.13.0 HmacCore::new_from_slice (src/block_api.rs:53–69), the inner-digest stack local in hmac 0.13.0 HmacCore::finalize_fixed_core (src/block_api.rs), reached by every scram::mac finalization and PBKDF2 PRF finalization, and PBKDF2 0.13.0’s running salt value and cloned keyed PRF locals (src/lib.rs:119–144). These primitive temporaries are not retained shim state, are never formatted and have no guaranteed stack erasure; zeroize features clear the HMAC/SHA-256 core state on drop but do not prove erasure of earlier copies. The shim writes HMAC finalization in scram::mac and the StoredKey SHA-256 finalization in scram::login directly into secret-owned output through finalize_into; it creates neither an ordinary returned HMAC output nor an ordinary stored-key digest array. Shim call sites are PBKDF2 derivation of SaltedPassword and HMAC derivation of ClientKey, ServerKey, ClientSignature and ServerSignature. Use pbkdf2 into secret-owned output, not pbkdf2_array’s returned value; decode salt and server signature and encode client proof through slice APIs into owned secret buffers. Password, salted password, keys, transcript and proof heap buffers remain secret-owned throughout. Compile-time carrier probes and sentinel Debug, Display and error witnesses establish that boundary; they make no claim to inspect the primitive stack residue. This is the explicit temporary-state disposition required by (`inv:observe:secret-boundary`), not permission for ordinary retained copies.

**Amendment (Transport evidence boundary)** · `amend:storage:transport-evidence-boundary` The pn-host fixture implements (`amend:storage:host-secured-evidence`) without a production executable, schema or persistence path. It accepts Unix sockets and numeric TCP endpoints, with no ordinary DNS hostname retained; direct secret acquisition and the public link-case refusal precede connection. The shim owns startup, SCRAM server-proof verification, real cancellation and whole private diagnostics; the driver receives only the public placeholder startup and cancellation key. Authentication uses the printable-ASCII password profile and a declared 100,000-iteration refusal bound; messages and configuration use a one-MiB representation bound. Public division-by-zero, cancellation and serialization-conflict diagnostics have explicit structural grammars; other diagnostics remain whole and secret-owned and terminate the stream. The reviewed statement and diagnostic surface must expand with storage shapes before enabling persistence; these limits do not clear the independent integration hold.


**Amendment (Closed storage statements)** · `amend:storage:closed-statements` Under (`inv:observe:secret-boundary`), pn-host exposes no raw driver client to a production caller. Only the storage module may issue a closed, reviewed statement vocabulary written beside its schema; it cannot select session or server reachability, identities or credentials as ordinary result rows. Transport fixtures reach the client only under cfg(test), never under a production feature. The public transport surface is acquisition, connect, cancel and draining whole private diagnostics. A compile-fail public witness and default/trace result-row sentinel scans guard this boundary. Storage statement and result shapes remain held until their own review; persistence stays disabled.

**Amendment (Authentication and frame bounds)** · `amend:storage:transport-bounds` (`amend:storage:host-secured-login`) accepts SCRAM iteration counts from 4,096 through 100,000 inclusive. PostgreSQL's default of 4,096 is the minimum: an impostor cannot choose a cheaper proof for an offline password search than that baseline; the upper bound limits unauthenticated work. This is a floor, not a claim that the default meets every deployment's password policy. The printable-ASCII password profile remains; malformed attributes, a non-extending nonce, a missing mechanism, a server error instead of the offer and both iteration bounds refuse before a client proof.
