**Model (Burn event and address)** · `model:devnet:burn` A qualifying event is a settled on-chain destruction output of the declared test asset with a positive, explicit integer amount and an independently checkable unspendable script. The output commits one permanent target burn address in its signed transaction before broadcast; missing, ambiguous or wrong-run target encodings are refused. The address is the declared chain-run identity paired with an opaque permanent name selected for the consumer's authenticated binding; it is not the destruction outpoint and makes no assertion about a person or wallet owner. Each destruction outpoint identifies one evidence event and contributes at most once to its committed target. Multiple fresh destructions may increase that target's amount; no event or already recorded amount may be moved, merged or reassigned to another address. Do not infer attribution from a change address, wallet label or mutable receipt. destroyamount illustrates on-chain destruction, but its ordinary null-data output alone supplies no target binding and its wallet comment is not on-chain evidence. The profile's target-bearing constructor and decoder require the evidence in (`amend:devnet:burn-targets`). Fees, ordinary transfers, grants, other assets and unconfirmed outputs contribute no burn amount.

**Rule (Mathematical interface)** · `rule:devnet:burn-map` The test burn-amount map at an address is the exact sum of distinct qualifying pinned destructions represented in the recognized marker policy's accepted sets and committed to that address, zero when none have been accepted, with 100000000 units per displayed token. Declare a bootstrap capacity bound of 1000000000000 units, backed by a fixed initial supply of that many units, no subsequent issuance of that asset, no reachable reissuance authority and no peg or subsidy minting it; the faucet opens at a published boundary strictly after the run starts, following a declared nonempty pre-opening interval. **Rule (Faucet budgets)** · `rule:devnet:faucet-limits` This is the published release schedule for the sole source of newly distributed test asset, drawn only from the fixed supply in (`rule:devnet:burn-map`), with no reissuance. Ordinary explicit transactions and a 4,096-entry block are heap witnesses. Use JSON-RPC 2.0 only: require jsonrpc equal to 2.0 as a string, an exactly matching request identifier and exactly one present result or error member; a successful null result is permitted only by that method's schema. Require strict UTF-8 JSON without a leading BOM. One monotonic wall deadline covers cookie acquisition, connection, request write, all reads and decoding; progress never renews it. Socket timeouts use only the remaining budget, and checks bracket cookie acquisition and typed decoding. This same-host profile assumes responsive local filesystem operations; the library cannot interrupt a stalled kernel filesystem syscall. This resource clock cannot enter a binding calculation. Allow one connection attempt per exchange and at most 8 attempts per 60 seconds per wallet instance, counted across callers before cookie access; saturation refuses locally and no retry loop bypasses it. These finite bootstrap limits bound repeated cookie reads and are tested with a controlled clock; later explicit retries consume the same budget. Elements is a trusted deployment component whose responses are taken as correct under its protocol. Parsed chain objects and service diagnostics are public under this service contract and remain fully observable. A protocol misbehaviour observed from the real daemon is an Elements bug to report upstream; crafted private echoes from an impostor are excluded by the host-secured path admission, not by a JSON-shape classification claim. Malformed-input unit tests establish the client parsers' own strictness and bounds. **Amendment (Genesis RPC evidence)** · `amend:devnet:wallet-rpc-evidence` The harness takes the Elements binary directory from PN_ELEMENTS_BIN and refuses before creating a fixture when it is unset or empty; the gate refuses in the same way, and no node toolchain path is committed. The genesis harness checks the exact binary, chain, public launch overrides, nontrivial challenge and raw genesis declaration in packages/wallet/provisioning.json before publishing its fixture. The client compares that supported declaration with the expected run, then checks getblockhash at height zero and the raw genesis header before returning a reader. Tests execute getblockcount, getblockhash, getblockheader and getblock against that real daemon; malformed HTTP and JSON remain parser-unit evidence. The five-method vocabulary also projects the signed-chain transaction fixtures of (`amend:devnet:wallet-signed-evidence`) through the existing adapter. The external harness owns a distinct rpcauth producer credential; the reader receives only its cookie-root descriptor and secret endpoint, port, relative cookie path and UID. Both credentials reach the same genesis. Cookie rotation is exercised across a real restart, followed by stale-cookie refusal and a later explicit fresh-cookie call. Gate port allocation holds this account's existing ownership mutex and draws from 42120–42159, disjoint from the PostgreSQL allocator's 42100–42119. Its probe binds with SO_REUSEADDR, as the daemon does, so connections the daemon closed first and that linger in TIME_WAIT do not count as taken, while a live listener does; allocators under other accounts share no mutex, so the scan starts at a random offset and a daemon that finds its probed port taken at launch starts again on another port, at most five times. The binary's version query writes a settings file into its data directory, so each fixture runs it in its own directory rather than the account's shared default, where concurrent queries race. A harness failure prints its error type and message, paths and ports included, since the fixture credential stays in the private producer file and no harness message carries it, and the tests include that line with the exit status; normal and failing exits stop owned nodes. The fixture challenge is P2PK over the secp256k1 generator, whose private key is the publicly known scalar 1. It suits an isolated fixture chain with networking disabled: the producer signs without holding a secret, while the node still validates every block signature. Signed fixtures under this challenge therefore witness the node's validation of block signatures, not the identity of the producer, since anyone can sign under it. A deployed development network needs an operator-held key, declared in an extended profile rather than by reusing this one. No local signature verification, recognition, settlement, production spending route or store-opening executable is admitted.


**Amendment (Signed fixture evidence)** · `amend:devnet:wallet-signed-evidence` The external harness uses Elements 29.4.1 RC 1 from the BDB-enabled toolchain, checks its declared version and launches the same nontrivial P2PK challenge from packages/wallet/provisioning.json. Its checked public overrides now include a 150-byte block-witness budget, legacy-wallet creation, unconfidential address selection, a finite fallback fee, a 100-byte relayed data-carrier size, which admits the declared run/target/request evidence script, and a chain without a parent: con_has_parent_chain=0 with a null parentgenesisblockhash, the pair the node requires together. The witness budget accommodates the node-produced signature and challenge script. The separately authenticated producer creates a legacy wallet, imports only the public scalar-one fixture key, and uses getnewblockhex, signblock, combineblocksigs and submitblock. The node rejects an altered signature with block-proof-invalid and a solved OP_TRUE replacement challenge with invalid-dyna-fed before accepting five signed blocks. Neither signing nor signature verification enters pn-wallet. The existing cookie reader receives no producer credential or wallet-selection authority; its closed raw block and transaction reads agree field-for-field with the independent byte oracle. Block 1 moves the single anyone-can-spend genesis output whole to a producer-owned fee reserve, because the node refuses an issuance whose entropy input is that genesis output. The producer then composes the initial issuance with the node's rawissueasset to an explicit, unconfidential producer-owned destination, has the node wallet sign it, and produces a grant-shaped transfer, another transfer and a one-token destruction using wallet methods. The issuance wallet method is not used for stock because it blinds its outputs. The initial fixture stock is 1,000,000,000,000 units, with zero reissuance-token amount and an asset distinct from the pegged fee asset; grants, fees and transfers contain zero explicit destruction of it, and the destruction output carries exactly 100,000,000 units. These are raw fixture amounts, not recognized or settled burn contributions. Exhibits: ``[WALLET-claim:wallet:rpc-signed-fixtures-match-independent-layouts]`` and ``[WALLET-claim:wallet:rpc-real-block-limit-holds-reader]``. The latter lowers the declared decoder byte limit below a real genesis block, observes Held with its locator and Bytes cause, and receives that same hold for subsequent count and different-block requests; a reader whose lowered response-byte ceiling admits the genesis header but not the genesis block holds in the same way. The reader does not skip the refused block.

**Amendment (Fixture supply limits)** · `amend:devnet:wallet-fixture-supply-limits` Genesis carries no test-asset output: its only funded output is one OP_TRUE output of 1,000,000,000,000 pegged-asset units with no reissuance token, and the independent oracle reconciles that output, its whole transfer to the producer-owned reserve in block 1 and the reserve's spending by the stock issuance. The fixed stock is that single explicit issuance of the declared 1,000,000,000,000 units with no reissuance token. Each supply path is tested on the signed chain. Reissuance: genesis and the stock issuance carry no reissuance token and the wallet reissuance call is refused, so the stock asset has no further supply. Issuance: any spender may still issue, but a later issuance creates a distinct asset, never stock units. Peg-in: with a parent chain declared and peg-in validation off, the node accepted a peg-in whose fabricated Bitcoin-format parent transaction and merkle proof met only the regtest work limit, and minted the pegged fee asset; validation would need a mainchain daemon, without which the node does not start. The profile therefore declares no parent chain, and the node refuses the same fabricated claim with "Constructed peg-in witness is invalid: Parent chain is not enabled on this network." Subsidy: con_blocksubsidy=0, and each fixture block's coinbase outputs total exactly that block's explicit fees, with zero in an empty block. General issuance remains a disclosed node capability that cannot mint the test asset. The accounting of every supported funding path and exclusive faucet distribution remain held; opaque change commitments are retained by both decoders rather than guessed as amounts. The five settlement cases formerly waiting for signed blocks now wait for real-chain recognition, lineage/opening validation and pinned-floor handling in the next slice. Signed-block availability alone closes none of those contracts. Operational distribution enforcement remains with bite 8, and snapshots with bite 5. Owned fixture nodes stop on normal return, failed production, test unwinding and catchable termination; the gate's exit cleanup also stops owned signed, rotation and settlement fixtures.

**Amendment (Settlement evidence carrier)** · `amend:devnet:wallet-settlement-evidence` pn-wallet carries the chain-evidence half of (`rule:devnet:settlement`) in its own types, with no domain prerequisite. A run's settlement carrier admits observations of the active chain: the tip height, the block hashes read at the heights a decision needs, and evidence located by transaction, output, block and height, whose explicit amount the evidence decoder selects. Evidence with fewer than 6 successor blocks is pending and recomputed on every observation; at 6 it pins once per outpoint. The floor is the highest pinned event's height and block hash, derived from the pinned evidence; there is no floor before any evidence pins, and later blocks without newly pinned evidence never move it. A locator whose block is not the active-chain hash at its height is refused as stale, an unread required height is refused as unavailable, one outpoint under different locators or amounts is refused as an alias, and a repeated report counts once. A replacement above the floor block changes only pending evidence, even where it reaches below the tip minus 6. A chain that no longer holds the floor block, by a different hash at its height or a lower tip, has replaced pinned evidence and is a realization fault for the run: the pinned total is retained, never edited downward, and every later observation returns the fault. The real-chain fixture sends explicit burn outputs: createrawtransaction writes the explicit burn output, its bare OP_RETURN script becomes the 100-byte evidence script before the node wallet signs, and sendrawtransaction receives the burn amount as its explicit unspendable-output allowance. Replacements use invalidateblock and freshly signed blocks that leave mempool evidence out, followed by blocks that re-include it. The node still serves a transaction from a replaced block, so only the active-chain hash check refuses that locator. Exhibits: ``[WALLET-claim:wallet:settlement-pins-at-declared-depth]``, ``[WALLET-claim:wallet:settlement-replacement-keeps-pinned-floor]``, ``[WALLET-claim:wallet:settlement-counts-each-outpoint-once]`` and ``[WALLET-claim:wallet:rpc-settlement-forks-keep-the-pinned-floor]``. Marker recognition with its buffer of 7, policy editions, marker lineage, accepted-set openings and the host's non-development refusal are not carried here; those cases stay held for the recognition slice that owns the pn-records carriers and the pn-host guard, and epoch snapshot derivation remains bite 5.
