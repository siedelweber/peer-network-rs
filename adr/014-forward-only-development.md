## Forward-only development · `sec:compatibility:record`

**Rule (Before the first stable release)** · `rule:compatibility:pre-one` Until the project's first 1.0 release, development is forward only. No stored data, database schema, encoding, dataset, label, command-line surface or library interface is kept compatible with an earlier pre-1.0 state. There are no migrations across pre-1.0 versions and no owed deprecation path: a store is rebuilt from the public inputs in the supported current representation. Retaining old readers, aliases or adapters is not a release obligation. Public inputs must be available for that rebuild; a private database is not their sole authority. This policy does not permit changing an assigned interchange theory or weakening a verdict about an unchanged public history.

**Justification (Freedom to correct)** · `just:compatibility:forward-only` Before stable adoption, a corrected model, smaller interface or stronger invariant is worth more than preserving accidental early representations. Maintaining migrations and obsolete interfaces would multiply the states every proof and fixture must cover before the supported contract has settled. A clear rebuild boundary makes those costs visible and allows a coherent current implementation, rather than an implicit promise whose evidence does not exist.

**Convention (Interchange assignment)** · `conv:compatibility:interchange` Project releases and interchange envelope versions are different axes. Repository external documents before project 1.0 use a declared experimental namespace and an explicitly assigned positive major; the initial assignment uses major one, and every incompatible subsequent assignment takes a fresh, previously unused major. A reader is promised the laws of its assigned major, including (`inv:interchange:minor-inclusion`) and (`law:interchange:major-boundary`), but the repository owes no reader for an earlier major under (`rule:compatibility:pre-one`). Minor inclusion and patch identity remain mandatory whenever those components are advanced. Assigned theories remain permanent under (`inv:interchange:permanence`); abandoning implementation support does not revise a theory or restamp an old document. Major zero is not an escape from these laws (`cav:interchange:genealogy`). Namespace allocation and actual theory assignment remain publication obligations, not facts established by this record. The local TOML/JSON dataset major supported by (`dec:render:policy`) is an engine admission rule, not the project release or an assigned external theory; it grants no cross-release dataset compatibility.

**Decision (Prepare history now)** · `dec:compatibility:history` Effective history is part of present correctness: the rules applicable at an old boundary must remain distinguishable from later rules. Build and test SCD2 now under (`rec:storage:decision`), including atomic succession and unchanged earlier verdicts. Before 1.0 these tests establish history semantics inside the supported implementation, not a migration or compatibility promise across implementations (`rule:compatibility:pre-one`).

**Convention (Stable adoption)** · `conv:compatibility:stable` At the first 1.0 release, clean upgrades of a running supported system become an obligation. That release must declare the supported persistent, encoding and public interface contracts and demonstrate its upgrade procedures, with SCD2 preserving effective history as new rule rows take effect. Schema transformations and software replacement still need their own reviewed procedures; SCD2 alone is not a schema migration system. This obligation is prospective and grants no retrospective migration from pre-1.0 stores. Within-major interchange laws continue unchanged.

**Gate (Release boundary)** · `gate:compatibility:release` Before 1.0, verify current contracts and rebuilding from public inputs without retaining obsolete compatibility machinery. Before declaring 1.0, require executed running-system upgrade evidence, historical verdict invariance and an explicit support policy under (`conv:compatibility:stable`). A passing current gate alone does not establish that release obligation.
