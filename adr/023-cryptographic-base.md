## Cryptographic base · `sec:crypto:record`

**Decision (Base library)** · `dec:crypto:base-library` Prefer Blockstream Research's secp256k1-zkp, the libsecp256k1 fork used by Elements, through its Rust bindings for the implementation's asymmetric cryptography. Use BIP-340 Schnorr where the implementation chooses a signature scheme and ECDSA where a protocol fixes it. One curve and one implementation lineage let act authentication, wallet operations and the Elements evidence in (`rec:devnet:decision`) and (`rec:storage:decision`) share reviewed machinery. The constant-time C lineage, extensive tests and published audits provide review depth; Elements-native commitment and proof modules avoid a second cryptographic library. These are reasons for a base, not a claim that every module or version shares one audit or that Rust bindings use a single C archive. The paper at network-v0.29.0 leaves the realization, key management and algorithm migration to deployment in ``rem:graph:authentication-realization-out-of-scope`` while requiring ``post:graph:act-authentication-requirements``. This record chooses implementation machinery, not a new paper premise.

**Rule (Operation scope)** · `rule:crypto:operation-scope` Use (`dec:crypto:base-library`) for signatures, curve key derivation and tweaking, and, when required and exposed by the admitted binding, multi-party and adaptor signatures, Pedersen commitments, range proofs and surjection proofs. For a transport the implementation defines itself, use its ECDH and ElligatorSwift key-agreement facilities; the symmetric half uses separately reviewed RustCrypto AEAD and HKDF primitives, as in the BIP-324 construction. ECDH alone does not authenticate a service, and this library choice admits no transport protocol. Services that require TLS retain a TLS integration under (`case:intranet:guarded`). Every standalone hash, MAC and KDF uses reviewed RustCrypto crates, including SHA-256 digests, HMAC, PBKDF2 and HKDF. Internal hashing within a base-library operation, including ECDH, BIP-340 and ElligatorSwift, belongs to that operation and is not a standalone primitive selection. The optional hashes feature of the base binding is not selected. Those primitives are within this division of work, not exceptions to the asymmetric base.

**Rule (Asymmetric exceptions)** · `rule:crypto:asymmetric-exceptions` Another asymmetric library requires a recorded exception naming the operation the base library cannot perform, the consumer or fixed protocol that requires it, the evidence of that limitation and the replacement's review. Missing bindings are an admission question, not permission to claim a capability or silently add another implementation. A protocol-fixed algorithm still uses the base where it supports that algorithm. Each exception preserves (`inv:observe:secret-boundary`) and records its feature and dependency cost.

**Amendment (Published binding boundary)** · `amend:crypto:binding-boundary` The evaluated secp256k1-zkp 0.11.2 re-exports secp256k1 0.29.1 for ECDSA, Schnorr, ECDH and ElligatorSwift, while secp256k1-zkp-sys 0.10.1 adds the Elements proof modules alongside secp256k1-sys 0.10.1. This is one implementation lineage but two compiled C source snapshots; it is not a claim of binary identity with a particular Elements release. ECDH and ElligatorSwift need no optional feature beyond the selected standard-library configuration. The published binding has adaptor, Pedersen, range and surjection interfaces but no public MuSig interface; a multi-party operation stays held until its binding and nonce discipline are admitted. The preference in (`rule:crypto:operation-scope`) does not invent that interface.

**Rule (Secret-owning integration)** · `rule:crypto:secret-integration` Cryptographic keys, nonce material, blinding factors and shared secrets remain secret-owned under (`dec:observe:secrets`) and (`inv:observe:secret-boundary`). A library type named SecretKey is not sufficient: the evaluated binding is copyable, its Debug exposes a key-derived fingerprint, explicit display helpers expose bytes, and optional serde permits secret serialization. Admission must prevent all such observation, prohibit secret serde opt-in, bound necessary primitive temporaries and establish owned erasure with reviewed data flow and adversarial witnesses. Entropy must come from a cryptographic source; random-generator trait bounds alone do not prove that property. Signing contexts require reviewed randomization and nonce handling. No key-bearing integration is admitted by naming the library.

**Open Question (Dependency and operation admission)** · `open:crypto:dependency-admission` Owner: the implementer of the first signing or verifying slice, with independent cryptographic integration review. Trigger: the first step that signs or verifies. Before enabling it, pin exact binding and transitive versions and archive checksums, review licences and C provenance, enabled modules, build scripts and the pinned toolchain, and demonstrate the required operation with independent vectors. Review secret ownership, diagnostics, temporary-state limits, entropy, context randomization and nonce reuse prevention under (`rule:crypto:secret-integration`). Unsupported multi-party bindings and any future transport construction remain separately held. No dependency, key-management system, signature recipe, commitment recipe or algorithm-migration protocol is admitted here; any new identity or signed-object recipe also passes (`gate:identity:implementation`).

**Amendment (Wallet operation scope)** · `amend:crypto:wallet-operation-scope` Bite 2's pn-wallet slice does not sign or independently verify block or transaction signatures, but its maintained codec eagerly parses untrusted confidential assets, values and nonces as Generator, PedersenCommitment and PublicKey through the binding's C. Range-proof metadata and surjection-proof encodings also enter C parsing; parsing does not verify those proofs. These are base-library operations and reach (`open:crypto:dependency-admission`) in bite 2, before the decoder is enabled. The point, commitment and proof parsers use the static no-precomputation context; they do not themselves dereference the randomized global context. Creation of the enabled global context is also a base-library operation in this slice's admission scope: establish whether the selected adapter paths initialize it, and review and exercise the allowed initialization path rather than inferring that a feature flag initializes it. Carry exact binding and transitive pins and archive checksums, both C snapshots' provenance and enabled modules, build scripts and the pinned toolchain, independent adversarial decoding vectors including invalid points, commitments and proof encodings, and the context's entropy source and lifetime. On the evaluated native target the global context initializes on first dereference through Once, randomizes with thread_rng and retains static process-lifetime state; rand's thread generator is OS-seeded. Admission must trace the pinned OS entropy route, test initialization failure and concurrent first use and review lifetime, fork and erasure implications; nonce-generation and key-custody duties are inapplicable only while no signing, key derivation or proof verification occurs. Structural decoding and node acceptance are never an independent signature verdict. Fixture signing and submission occur through the separate harness route of (`amend:devnet:wallet-first-evidence`); later wallet spending remains daemon-signed with keys in daemon custody. Local signing would duplicate that custody and recovery; local signature verification additionally needs challenge/script and sighash interpretation. Keep the maintained decoder for full transaction layouts, with a byte-level decoder carrying opaque, prefix-checked commitments as the fallback if admission cannot bound C parsing and context behaviour. No fallback is silently admitted. Offline block-signature evidence follows (`amend:devnet:wallet-evidence-stages`).

**Amendment (Wallet codec feature boundary)** · `amend:crypto:wallet-codec-features` The elements 0.27.0 evaluation resolves secp256k1-zkp 0.11.2 with actual-rand, default, global-context, hashes, rand-std and std, and secp256k1 0.29.1 with alloc, default, global-context, hashes, rand, rand-std and std (`amend:crypto:binding-boundary`). It includes rand 0.8.8, rand_chacha 0.3.1, rand_core 0.6.4, getrandom 0.2.17 and bitcoin_hashes 0.14.101 and 1.2.0. Disabling elements' default features does not disable this unified dependency feature set. This evaluated exception to (`rule:crypto:operation-scope`) is confined to the decoder and is not operation admission. Before enabling bite 2, mechanically compare the resolved unified binding features and package versions against the reviewed manifest/lockfile feature record, and reject drift. An import/path and dependency check permits first-party use of SECP256K1 and the codec's hash paths only inside pn-wallet's named decoder adapter, catches aliases and re-exports with negative probes, and rejects first-party use elsewhere; inspect transitive paths and generated code separately instead of calling a textual check complete data-flow proof. Cargo unification is not module isolation. Permit only layout decoding, serialization and fixed external chain-locator recipes there, never signing or new semantic digests; independently recompute required locator hashes through the reviewed RustCrypto route (`gate:identity:implementation`). Admit C parsing and any global-context initialization under (`amend:crypto:wallet-operation-scope`), preserve both C snapshots' notices, and keep key-bearing and secret-serde paths outside the interface. A later signature operation requires its own operation evidence even if these features are already linked.


**Amendment (Wallet parsing admission)** · `amend:crypto:wallet-parsing-admission` The public-layout decoder pins elements 0.27.0, secp256k1-zkp 0.11.2, secp256k1 0.29.1 and both sys crates at 0.10.1, with the reviewed unified features of (`amend:crypto:wallet-codec-features`). secp256k1-sys bundles upstream revision 1ad5185cd42c0636104129fcc9f6a4bf9c67cc40 and enables ECDH, SCHNORRSIG, EXTRAKEYS and ELLSWIFT; secp256k1-zkp-sys bundles upstream revision 6152622613fdf1c5af6f31f74c427c4e9ee120ce and enables SURJECTIONPROOF, GENERATOR, RANGEPROOF, ECDSA_ADAPTOR and WHITELIST. Their depend/secp256k1-HEAD-revision.txt files state provenance; build.rs compiles lax_der_parsing.c, precomputed_ecmult_gen.c, precomputed_ecmult.c and secp256k1.c through cc. The pinned compiler is nightly-2026-10-16. hex_lit 0.1.1 and bitcoin-private 0.1.0 also run build.rs, querying RUSTC --version and emitting compiler-version configuration flags; each recorded build-script path is checked against Cargo metadata custom-build targets. Adapter re-exports, public codec aliases and signatures, and production SECP256K1 uses are mechanically refused with negative witnesses. The detached fuzz notice carries the NCSA terms and the bundled LLVM exception as well as MIT and Apache terms. Both C archives and their notices remain distinct; no binary identity with the Elements node is claimed. The upstream source snapshots contain tests and Valgrind constant-time CI, but no executed coverage-guided campaign result is inferred from those files. The bindings' secp256k1_fuzz configuration substitutes noncryptographic behaviour and is not used. The adapter campaign is recorded in (`amend:devnet:wallet-fuzz-campaign`).

**Amendment (Context admission remainder)** · `amend:crypto:wallet-context-remainder` The decoder's point, commitment and proof parsers use static no-precomputation contexts. Owner: wallet cryptographic integration implementer. Entropy-failure execution and fork-sensitive use remain held before admitting a key-bearing or global-context production path. This is a scoped public C-parsing candidate, not closure of (`open:crypto:dependency-admission`). Its executable evidence is ``[WALLET-claim:wallet:invalid-curve-encodings-refuse]``, (`claim:discipline:wallet-codec-paths-stay-confined`) and (`claim:discipline:wallet-development-edges-stay-out-of-production`); the unexecuted entropy-failure case keeps (`verif:devnet:wallet-crypto`) held.
