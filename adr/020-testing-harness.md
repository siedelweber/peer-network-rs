## Testing harness · `sec:harness:record`

**Decision (Evidence at several levels)** · `dec:harness:levels` Every first-party crate has unit, crate-level and integration tests from its first implementation bite, including infrastructure, client and test-support crates. Unit tests exercise local invariants beside their code in test modules; external crate-level tests in tests/public.rs exercise only the crate's public surface; tests/integration.rs and its modules under tests/integration/ exercise composition with dependencies, including error and resource boundaries. A dependency-free crate still tests its public boundary with the standard library, serialization or process environment it actually uses, not an invented domain dependency. Binary packages expose their command logic for unit and public-surface tests and exercise process behavior in integration tests. These levels distinguish failures and evidence scope; duplicating an assertion at three sites is not three independent oracles. Vendored packages remain under their existing policy (`dec:lint:policy`).

**Rule (Claims at test sites)** · `rule:harness:claims` Every test follows (`rule:testing:site`): a meaningful gloss, then its authored claim mint or a parenthesised citation to the single existing mint, then its derived test label. Harness-generated cases need a checked generator-to-test mapping; helper names and suite names do not mint claims. A shared suite's first establishing test mints the scoped statement and other implementation runners cite it with their own test labels and declared owner imports. Keep implementation identity, contract edition, test level, input case and execution configuration in results so all supporting executions join under (`rule:testing:results`). Registers, paper exhibition/import, explicit holds and obligation coverage remain (`rec:testing:decision`). A new harness changes how evidence is obtained, not what a passing claim means.

**Rule (Conformance suites)** · `rule:harness:conformance` A conformance suite is one reviewed set of claim-bearing cases and expected predicates for a versioned public contract, run unchanged against every implementation of that contract. Thin adapters translate setup, operations and observed results without supplying expected values or removing difficult cases. Run the same case identifiers, boundary values, operation histories and predicates against the production implementation, each functional mock and any independent implementation admitted for comparison. A missing required capability fails conformance; selecting a weaker subset requires a separately named supported contract and cannot count as the original contract passing. Include the paper's vectors and theorem-derived obligations through repository claims, the API's typed CBOR and outcome rules, storage history and the burn adapter's evidence rules. Apply (`conv:xchg:metatheorems-as-tests`) for canonical vectors and generated laws; finite tests establish their scoped cases, not unrestricted mathematical theorems. Production/mirror agreement alone is not an oracle.

**Rule (Properties and replay)** · `rule:harness:properties` Generate valid and deliberately invalid structures, boundary histories and operation sequences from the design's invariants. State generator domains, distributions, size and work limits, oracle independence and the premise each shrink must preserve. Shrink a failing history to a smaller witness without silently removing its required precondition; retain both original and minimized inputs. Record the deterministic seed, generator and shrinker editions, configuration, case count and explicit scheduling/fault choices so failure can replay. A seed alone is insufficient across generator or dependency changes, so preserve the final exact witness as a reviewed regression case. Fixed regression seeds and a bounded declared seed set run on every change; additional recorded seeds and larger ranges extend coverage on capable workers. Random selection is outside binding computation. Assertion failure remains failure even if another seed passes; a cancelled search is incomplete, not evidence of no counterexample (`rule:testing:results`).

**Model (Functional substitutes)** · `model:harness:mocks` A functional mock is a working implementation of the contract at the declared abstraction boundary, not a table of canned replies. The in-memory storage implementation maintains immutable payloads, append-only closures, total half-open SCD2 histories, consistent as-of reads, serialized atomic close/open and rollback. The simulated development chain maintains asset balances and supply, attributed destruction, pending and pinned events, depth, provenance and fork/fault transitions; it distinguishes grants from burns and exercises refusal paths. Controlled scheduling and injected faults make hard histories reproducible. These implementations must pass (`rule:harness:conformance`) before tests use them as admitted substitutes; until then their dependent evidence is held. Small isolated stubs may probe a local error branch only when labelled as stubs, and never discharge storage or burn conformance. Model correctness proves no PostgreSQL durability, network availability, signer trust, chain consensus or economic costliness (`cav:devnet:assurance`).

**Rule (Real services remain required)** · `rule:harness:real-services` Fast runs name their mock implementations and contract editions in every result. The storage conformance suite also runs against the supported real PostgreSQL beta under (`gate:storage:evidence`); the burn suite also runs through the real Elements adapter and signed asset chain under (`gate:devnet:implementation`). Keep shared contract cases identical and add separately labelled service-specific tests for SQL concurrency, persistence/restart, RPC decoding, signatures and transport failures. Compare semantic results at declared effective boundaries, not incidental timestamps, ports or generated chain identifiers. Missing provisioned services fail the service tier rather than selecting mocks, skipping cases or producing an aggregate green verdict. Passing mock tests is noticed partial evidence until required real executions for the same source and contract are joined. The amendment (`amend:storage:conformance`) makes this explicit without weakening the real-instance gate.

**Rule (Benchmark evidence)** · `rule:harness:benchmarks` Benchmark named workloads under (`expt:design:workloads`): construction, compilation, numerical refinement, publication, replay, raw traversal, storage histories, API encoding/execution and client workflows. Separate setup, warmup, steady work and teardown; record elapsed wall seconds, work counts, throughput units, peak memory where measurable, evidence bytes, refusal behavior and observation overhead. State whether CPU/allocation measures are unavailable rather than zero. Store raw samples and machine-readable summaries as untracked run artifacts under .lane/benchmarks and retain them in the gate's artifact store; reviewed workload/baseline/threshold declarations are data, not invented measurements in prose. Record source, toolchain, dependency/service versions, CPU, resource isolation, features, input/seed, observation mode and warmup/sample policy. Compare only compatible runs with predeclared statistical and practical thresholds; a repeatable exceeded threshold is a warning and a regression finding attached to its workload claim, never a failing test, performance tier or gate (`rule:devperf:nonverdict`). Noise, incompatible baselines or missing measurements produce an explicit inconclusive/held performance assessment, never a claim of measured feasibility; the functional verdict remains unchanged. Baseline replacement requires a reviewed reason, not automatic acceptance of the new result. Timing observes execution and cannot choose a binding verdict (`inv:observe:noninterference`). Apply the budgets, comparison and registry rules of (`rec:devperf:decision`); retain all evidence and owned findings, and never rerun or skip a test because of duration.

**Signature (Client operations)** · `sig:harness:clients` pn-client receives and answers CBOR-native GraphQL under (`rec:api:decision`), and speaks that same language to the network node pn. Its caller interface is GraphQL request and response bytes through one execution entry point, not a parallel Rust operation API. Relay the node's submit, read, fetch and other supported operations, and add client workflows for faucet funding, burning to a new account, burning to an existing account and recovery (`dec:harness:client-schema`). Account remains the existing authenticated actor and permanent burn binding, not a new domain object. pn-wallet owns the development wallet's funding and spending workflow; pn-client supplies its node GraphQL transport without a reverse package dependency. New-account work prepares or resolves the authenticated binding and preserves keys in secret carriers; existing-account work validates the permanent binding before fresh destruction. A gift burn consumes fresh spendable tokens, never moves earlier burn value. A grant, broadcast or receipt is not admitted standing, and all stages return explicit GraphQL outcomes.

**Rule (Client burn workflow)** · `rule:harness:burn-targets` pn-wallet owns development funding, construction, signing, broadcasting and recovery through the Elements wallet RPC. The Elements wallet is the source of truth for created transactions and spent inputs, so recovery queries it through pn-wallet before any new spend. Keep the request association and recoverable transaction in that wallet's durable state under (`rule:harness:wallet-recovery`); the client has no independent PostgreSQL or local-file recovery journal. The wallet already persists spending, and a second authority could disagree with it while forcing a client tool to operate a database. Return stage-specific GraphQL receipts for preparation, funding, construction, broadcast, settlement and submission. Cancellation or lost replies preserve uncertainty, never imply rollback or authorize another payment. A successful RPC is not settlement or admission. Wallet RPC is the wallet channel only; the client and node interfaces remain GraphQL.

**Rule (Wallet request recovery)** · `rule:harness:wallet-recovery` Bind an opaque request identifier within one declared run and selected wallet to the complete immutable typed intent: operation, asset, amount, permanent target, authenticated binding and allowed fee policy.
