## Testing harness · `sec:harness:record`

**Decision (Evidence at several levels)** · `dec:harness:levels` Every first-party crate has unit, crate-level and integration tests from its first implementation bite, including infrastructure, client and test-support crates. Unit tests exercise local invariants beside their code in test modules; external crate-level tests in tests/public.rs exercise only the crate's public surface; tests/integration.rs and its modules under tests/integration/ exercise composition with dependencies, including error and resource boundaries. A dependency-free crate still tests its public boundary with the standard library, serialization or process environment it actually uses, not an invented domain dependency. Binary packages expose their command logic for unit and public-surface tests and exercise process behavior in integration tests. These levels distinguish failures and evidence scope; duplicating an assertion at three sites is not three independent oracles. Vendored packages remain under their existing policy (`dec:lint:policy`).

**Rule (Claims at test sites)** · `rule:harness:claims` Every test follows (`rule:testing:site`): a meaningful gloss, then its authored claim mint or a parenthesised citation to the single existing mint, then its derived test label. Harness-generated cases need a checked generator-to-test mapping; helper names and suite names do not mint claims. A shared suite's first establishing test mints the scoped statement and other implementation runners cite it with their own test labels and declared owner imports. Keep implementation identity, contract edition, test level, input case and execution configuration in results so all supporting executions join under (`rule:testing:results`). Registers, paper exhibition/import, explicit holds and obligation coverage remain (`rec:testing:decision`). A new harness changes how evidence is obtained, not what a passing claim means.

**Rule (Conformance suites)** · `rule:harness:conformance` A conformance suite is one reviewed set of claim-bearing cases and expected predicates for a versioned public contract, run unchanged against every implementation of that contract. Thin adapters translate setup, operations and observed results without supplying expected values or removing difficult cases. Run the same case identifiers, boundary values, operation histories and predicates against the production implementation, each functional mock and any independent implementation admitted for comparison. A missing required capability fails conformance; selecting a weaker subset requires a separately named supported contract and cannot count as the original contract passing. Include the paper's vectors and theorem-derived obligations through repository claims, the API's typed CBOR and outcome rules, storage history and the burn adapter's evidence rules. Apply (`conv:xchg:metatheorems-as-tests`) for canonical vectors and generated laws; finite tests establish their scoped cases, not unrestricted mathematical theorems. Production/mirror agreement alone is not an oracle.

**Rule (Properties and replay)** · `rule:harness:properties` Generate valid and deliberately invalid structures, boundary histories and operation sequences from the design's invariants. State generator domains, distributions, size and work limits, oracle independence and the premise each shrink must preserve. Shrink a failing history to a smaller witness without silently removing its required precondition; retain both original and minimized inputs. Record the deterministic seed, generator and shrinker editions, configuration, case count and explicit scheduling/fault choices so failure can replay. A seed alone is insufficient across generator or dependency changes, so preserve the final exact witness as a reviewed regression case. Fixed regression seeds and a bounded declared seed set run on every change; additional recorded seeds and larger ranges extend coverage on capable workers. Random selection is outside binding computation. Assertion failure remains failure even if another seed passes; a cancelled search is incomplete, not evidence of no counterexample (`rule:testing:results`).

**Model (Functional substitutes)** · `model:harness:mocks` A functional mock is a working implementation of the contract at the declared abstraction boundary, not a table of canned replies. The in-memory storage implementation maintains immutable payloads, append-only closures, total half-open SCD2 histories, consistent as-of reads, serialized atomic close/open and rollback. The simulated development chain maintains asset balances and supply, attributed destruction, pending and pinned events, depth, provenance and fork/fault transitions; it distinguishes grants from burns and exercises refusal paths. Controlled scheduling and injected faults make hard histories reproducible. These implementations must pass (`rule:harness:conformance`) before tests use them as admitted substitutes; until then their dependent evidence is held. Small isolated stubs may probe a local error branch only when labelled as stubs, and never discharge storage or burn conformance. Model correctness proves no PostgreSQL durability, network availability, signer trust, chain consensus or economic costliness (`cav:devnet:assurance`).

**Rule (Real services remain required)** · `rule:harness:real-services` Fast runs name their mock implementations and contract editions in every result. The storage conformance suite also runs against the supported real PostgreSQL beta under (`gate:storage:evidence`); the burn suite also runs through the real Elements adapter and signed asset chain under (`gate:devnet:implementation`). Keep shared contract cases identical and add separately labelled service-specific tests for SQL concurrency, persistence/restart, RPC decoding, signatures and transport failures. Compare semantic results at declared effective boundaries, not incidental timestamps, ports or generated chain identifiers. Missing provisioned services fail the service tier rather than selecting mocks, skipping cases or producing an aggregate green verdict. Passing mock tests is noticed partial evidence until required real executions for the same source and contract are joined. The amendment (`amend:storage:conformance`) makes this explicit without weakening the real-instance gate.

**Rule (Benchmark evidence)** · `rule:harness:benchmarks` Benchmark named workloads under (`expt:design:workloads`): construction, compilation, numerical refinement, publication, replay, raw traversal, storage histories, API encoding/execution and client workflows. Separate setup, warmup, steady work and teardown; record elapsed wall seconds, work counts, throughput units, peak memory where measurable, evidence bytes, refusal behavior and observation overhead. State whether CPU/allocation measures are unavailable rather than zero. Store raw samples and machine-readable summaries as untracked run artifacts under .lane/benchmarks and retain them in the gate's artifact store; reviewed workload/baseline/threshold declarations are data, not invented measurements in prose. Record source, toolchain, dependency/service versions, CPU, resource isolation, features, input/seed, observation mode and warmup/sample policy. Compare only compatible runs with predeclared statistical and practical thresholds; a repeatable exceeded threshold is a warning and a regression finding attached to its workload claim, never a failing test, performance tier or gate (`rule:devperf:nonverdict`). Noise, incompatible baselines or missing measurements produce an explicit inconclusive/held performance assessment, never a claim of measured feasibility; the functional verdict remains unchanged. Baseline replacement requires a reviewed reason, not automatic acceptance of the new result. Timing observes execution and cannot choose a binding verdict (`inv:observe:noninterference`). Apply the budgets, comparison and registry rules of (`rec:devperf:decision`); retain all evidence and owned findings, and never rerun or skip a test because of duration.

**Signature (Client operations)** · `sig:harness:clients` Provide a reusable client library and a command-line client for people and tests over (`rec:api:decision`). Offer one-step workflows to request faucet tokens, burn fresh test asset for a newly created account, burn fresh test asset for an existing account, submit a proposed act, read standing/title, fetch exact publications and recover durable operation status. Account is client vocabulary for the existing authenticated actor and permanent burn binding, not a new domain object. Requests and results use native CBOR scalars; canonical packages remain exact byte strings. New-account work creates or resolves the actor's authenticated binding through the existing public act contract and preserves its keys in secret carriers. Existing-account work resolves and validates the established binding before committing new destruction to it. Burning for another account consumes fresh spendable tokens from the sender; it never transfers previously recorded burn value or rewrites a binding. A faucet grant is only funding, and a burn or submission is never labelled admitted standing before the existing gates pass.

**Rule (Client burn workflow)** · `rule:harness:burn-targets` The development burn constructor commits the permanent target burn address inside the unspendable output before signing and broadcasting, under (`amend:devnet:burn-targets`). Validate the target's run and authenticated binding, exact amount, asset and fee budget before irreversible work; a new account must have a durable recoverable local/public binding plan, and an existing account must not be replaced by a new address merely to fit the helper. Return stage-specific receipts for account preparation, funding, transaction construction, broadcast, settlement and act submission; one-step convenience is not atomicity across them. The library takes an explicit durable recovery-journal contract; the development command implements it with private PostgreSQL state, not a host-internal API or a plain local file. Persist recovery state and the exact signed transaction before broadcast, reuse request identifiers and those bytes on retry, and resume or report uncertainty rather than paying again after a lost reply. Cancellation after a possible effect reports that uncertainty. The client waits for declared settlement evidence or returns pending; a successful RPC does not prove destruction or admission. The wallet/Elements call needed to construct a development burn is a narrowly scoped local deployment adapter, not an arbitrary RPC endpoint added to the public API.

**Rule (Client output and custody)** · `rule:harness:client-output` The command uses cli-common and (`rec:output:decision`): one JSON result object plus newline on successful completion, JSON diagnostics/traces on stderr, terminal stdout refused before effects, and the existing usage/runtime exit classes. A returned pending receipt is an explicit completed status query, never a claim that the underlying workflow settled. CLI JSON is the command's presentation contract, not JSON GraphQL; exact returned package bytes go to an explicitly requested artifact and the result describes it, rather than decoding and re-encoding them through JSON. Reusable libraries install no subscriber or exporter. Instrument client stages, retries, work and wall time under (`rec:observe:decision`); record all public inputs/results/errors and keep wallet keys, credentials, endpoint details and complete private operating settings secret-typed from acquisition. Tests and helpers get no exception to this rule. Recovery and profile settings live in the database or public inputs under (`rule:storage:configuration`); no second policy configuration file or tracked secret store is introduced. Surfaces and fixtures may change freely before 1.0 (`rule:compatibility:pre-one`).

**Proposal (Harness dependencies)** · `proposal:harness:dependencies` For owner acceptance, propose proptest for bounded generation and shrinking, Criterion for benchmark measurement and statistical comparisons, and tokio for asynchronous test scheduling and the client's async execution. Retain the ordinary Rust test runner for unit, crate and integration entry points and a checked structured result collector for their claim links. These roles address counterexample reduction, repeatable measurements and async cancellation without changing domain laws. Review versions, licences, features, seed/replay behavior, runtime control and secret-safe errors before adoption; no compatible version set is asserted here. Criterion integration must use a reviewed runner that preserves (`rec:output:decision`) and owns output streams rather than admitting uncontrolled harness printing. Client HTTP/CBOR dependencies follow the exact-value review of (`proposal:api:dependencies`), with pn-interchange for canonical documents and secrecy for private material. Choosing a library does not establish evidence independence or correct integration.

**Proposal (Packages and dependency direction)** · `proposal:harness:packages` Propose pn-testkit as a development-only support crate for generic contract runners, independent models, generators, functional mocks and fault control. It imports no production domain crate; tests adapt typed public contracts through generic operations and carriers, preventing a development-dependency cycle with the crate under test. Keep domain-specific conformance instances, independent mathematical oracles and cross-crate clients in pn-verification, which grows as an outer consumer from the first domain bite. Production crates may use pn-testkit only as a development dependency and never depend on pn-verification; no production answer comes from a mock. Propose pn-client with public dependencies on pn-records and pn-interchange plus reviewed HTTP/CBOR transport, and pn-command as the command package depending on pn-client and cli-common. Propose optional PostgreSQL recovery-journal and Elements RPC dependencies in the command for the development wallet workflow, with interfaces injected into the client so read-only public API use needs neither service. Those adapters are reviewed with (`proposal:design:devnet-adapter`); it must not import host internals or bypass public admission. The server does not depend on its client. These packages and edges require review against record 007; the adopted graph is not amended here.

**Rule (Execution tiers)** · `rule:harness:tiers` On every change, run existing repository checks, all available unit/public-surface/integration tests using declared functional substitutes where appropriate, shared conformance for each available pure/mock implementation, bounded property cases with recorded seeds, benchmark correctness/smoke cases and client tests for its available surface. A separately named service tier runs the same storage and burn suites against their real services, API/client end-to-end cases and service-specific faults on provisioned workers. A measured performance tier runs on declared suitable workers; expanded property searches supplement the bounded set. From a bite claiming the corresponding supported surface, service results are mandatory for that source before its gate is green; relevant workload/resource/dependency changes also require the performance tier and its reviewed baseline. A fast-only result is partial and cannot satisfy a service-dependent record gate. Publish a source/configuration/implementation/tier matrix with every required result, failure and hold; unavailable workers leave the obligation held rather than silently reducing the matrix. No provisioning is performed by this decision.

**Gate (Harness foundation)** · `gate:harness:foundation` In the shared foundation bite before record 007's first domain bite, establish the level/suite/implementation registry and result join, review the proposed dependencies and support package, and apply the three test levels to documents, pn-interchange, cli-common and execwrap. Preserve and extend the canonical-vector/property practice of (`conv:xchg:metatheorems-as-tests`). Exercise missing levels, unregistered implementations, dropped suite cases, missing seeds, ignored tests, mock results misreported as real, stale source results and benchmark correctness failures as negative probes. Timing-only regressions must instead preserve passing verdicts while emitting warnings and findings under (`rule:devperf:nonverdict`). Check test-site claims, owner registers and item-local lint discipline without test suppressions (`rec:testing:decision`), (`dec:lint:policy`). Later domain crates must be born with their local/public/integration tests and first conformance claims; the full corpus is not deferred wholesale to the final bite. The implementing foundation and bite owners close the explicit holds in (`open:design:harness-evidence`); this record creates no harness code or executed test evidence.

**Amendment (Timing findings)** · `amend:harness:performance-findings` The benchmark rule and foundation probes now separate performance findings from correctness (`rule:harness:benchmarks`), (`gate:harness:foundation`). This supersedes the earlier instruction that repeatable benchmark regressions fail a required tier: timing never fails a test, tier or gate under (`rule:devperf:nonverdict`). Required runs, baselines, retained samples and finding ownership remain obligations; an inconclusive comparison is a disclosed performance-evidence hold, not a timing-derived functional failure. The performance foundation adds the collector and the warning path while preserving claim-based semantic results.
