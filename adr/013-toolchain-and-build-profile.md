## Toolchain and build profile · `sec:toolchain:record`

**Decision (Compiler)** · `dec:toolchain:compiler` The workspace uses the latest Rust nightly with rustfmt and Clippy, because maintaining one current development environment avoids accumulating workarounds for an obsolete compiler. The build-environment maintainer keeps that compiler current; a compiler more than two days old is an error of that maintenance process and is repaired there. An older compiler is not selected to make a change pass.

**Decision (Minimum compiler)** · `dec:toolchain:minimum` The workspace and its first-party members declare no minimum compiler version, because development targets the current nightly under (`dec:toolchain:compiler`) rather than support for older compilers.

**Decision (Release profile)** · `dec:toolchain:release` Releases use thin LTO and 1 codegen unit. Thin LTO provides most of full LTO's cross-crate inlining at a fraction of its link time, and one codegen unit lets the optimiser see each crate whole. Dev and test profiles retain Cargo defaults so gate builds keep their incremental speed; changing their optimisation levels requires later measurement.

**Gate (Verification)** · `gate:toolchain:verification` The build-environment maintainer checks the answering compiler and the availability of its rustfmt and Clippy components against (`dec:toolchain:compiler`), because a channel name alone does not establish which compiler runs. An unavailable component or an out-of-date compiler is an environment defect; it is not repaired by weakening the workspace lints or selecting an older compiler. The repository verification entry (`gate:foundation:verification`) uses that maintained environment and does not require equality with a compiler commit stored in the repository.

**Amendment (Development performance measurements)** · `amend:toolchain:development-performance` The current defaults and refusal of dev/test overrides remain the implemented policy until the foundation bite of (`gate:devperf:foundation`). That bite measures and decides the dev/test settings under (`dec:devperf:profiles`), then updates the profile declarations, checker and witnesses together to enforce the reviewed choices. This refines (`dec:toolchain:release`) and (`gate:toolchain:verification`) without changing the compiler policy or the release profile. Build-time excess is a warning and an owned misconfiguration finding, never a failing gate verdict (`rule:devperf:builds`), (`rule:devperf:nonverdict`).

**Amendment (Measured gate profile)** · `amend:toolchain:measured-gate-profile` This settles (`amend:toolchain:development-performance`) and refines (`dec:toolchain:release`) and (`gate:toolchain:verification`) through the measured choice in (`amend:devperf:measured-choices`). Adopt a named gate profile inheriting dev with optimization level 1, debug information 0, debug assertions true and overflow checks true. Ordinary dev and test retain their debugging defaults, and release is unchanged. In the one-setting-at-a-time campaign, median warm test times were 6.987 seconds at optimization 0/debug 2, 7.573 seconds at optimization 0/debug 0 with variable contention, and 4.571 seconds at optimization 1/debug 0; median document checks were 0.678, 0.603 and 0.357 seconds. Cold test builds were 15.198, 15.366 and 23.529 seconds. Removing debug information alone is not claimed to speed test execution. The chosen gate profile trades a bounded cold cost and gate-only symbols for recurring execution and link savings; debugging remains available through the unchanged dev/test profiles. The independent profile campaign measured comment-only documents rebuild medians of 0.627 seconds before and 0.475 seconds after; this measures front-end and relink cost, not a changed implementation workload. The build-policy checker requires exactly the reviewed release and gate profiles and continues to refuse dev/test overrides. Its witnesses reject changed optimization or symbols and disabled debug assertions or overflow checks. Gate Clippy, test, documentation and document-engine commands select the same named profile; timing findings remain separate from their semantic status. A second optimized profile and its compile-time kind selection are implemented in the common-boundary cut: release-debug inherits release, retains its optimization, LTO, codegen units, assertion, overflow and panic settings, and adds debug information level two with no stripping. Its reviewed recipe also selects the production debug-observation feature; release uses the release profile without that feature. The feature fixes the kind at compile time, while the recipe binds kind to the effective profile and feature pair. A profile name or debug_assertions alone cannot identify the kind. Ordinary dev/test and the gate profile remain unchanged. The exact profile checker, build-policy dataset, feature classifications and their witnesses admit the third profile with the manifest. Separately compiled shipped recipe artifacts are registered and controlled at their package-scoped profile and feature selections; their warm gate-step cost is measured under (`rule:devperf:measurement`) without a speed verdict; a clean-build figure with empty target artifacts and compiler-cache misses remains owed. The existing protected-package selection separately admits the debug generator under (`amend:decomposition:protected-package-resolution`). Added gate-build cost is measured under (`rule:devperf:builds`) and (`rule:devperf:nonverdict`), not inferred from this design.

**Amendment (Dated compiler)** · `amend:toolchain:dated-compiler` The compiler selection follows (`dec:toolchain:compiler`), replacing a retained dated installation with maintenance of the latest nightly because a reproducible development-tool pin is not a product contract. Recorded compiler identities remain facts about their recorded runs, not selections for later runs. Dependency API, feature, platform and numerical-premise review remains the dependency owner’s duty; compiler freshness does not admit an unreviewed dependency or establish numerical soundness.

For the native numerical surface of (`rule:design:binary64-evidence`), compiler maintenance precedes testing a candidate dependency, while the dependency’s admission still requires review of its used APIs, features, fault mappings and arithmetic premises. A failed build identifies work in the environment or consumer; it supplies neither dependency admission nor a reason to retain an obsolete compiler.

**Amendment (Build composition)** · `amend:toolchain:build-composition` Rust work uses Cargo with the maintained compiler of (`dec:toolchain:compiler`) and the selected profiles and features, because the result concerns the code that was actually built. The entry is (`gate:foundation:verification`); the retained build graph is not an additional verification prerequisite.
