# Credential derivation · `rec:derivation:scope`

**Definition (Scope)** · `def:derivation:scope` Implements the shared primitive boundary of (`[ROOT-dec:observe:credential-packages]`) using the exact roots admitted by (`[ROOT-amend:storage:transport-dependencies]`). It owns no password, allocation, transport, scheduler, limiter, mapping or entropy source. Errors contain only the bound or primitive refusal class. The host retains its existing transport and measured ceiling under (`[ROOT-amend:storage:measured-scram-ceiling]`); this package grants no protected-home consumer admission.

**Definition (Borrowed primitive views)** · `def:derivation:borrows` Input and Output are single-call views of an already authorized caller borrow, with constant role-only Debug. Their tuple fields receive that borrow; neither acquires a protected container nor creates a byte accessor to one. The caller owns protection and labels the exit before constructing the view, and the operation consumes the view without retaining it. Output is written in place and is never returned as an ordinary secret array. Observation records every available public argument and the content-free result; it cannot format either view's contents. This interface does not authorize a callback or writer over protected-home bytes.

**Definition (Primitive operations)** · `def:derivation:primitives` SaltedPassword uses the existing PBKDF2 HMAC-SHA-256 into a 32-byte destination at 4096 through 600000 rounds. Password, salt, keyed input and message are each bounded by the host's one-MiB buffer limit. INPUT_LIMIT, MIN_ITERATIONS, MAX_ITERATIONS and KEY_LENGTH expose these unchanged bounds; the host asserts equality with its admission limits at compile time, before any executable can accept a widened bound independently of this library. A runtime-only check is set aside because it would discover that mismatch after building the consumer. SALT_LENGTH and VERIFIER_LENGTH expose the restricted formatter's exact lengths. Keyed values use HMAC-SHA-256 with the supplied protocol message; Client Key and Server Key remain distinct messages. StoredKey hashes exactly the 32-byte client key. Each output is exactly 32 bytes; length and work-factor refusals precede writes. These are the protocol operations of RFC 5802 section 3 as specialized by [RFC 7677 section 3](https://www.rfc-editor.org/rfc/rfc7677.html#section-3), not new identity recipes.

**Definition (Verifier formatting)** · `def:derivation:verifier` The restricted verifier of (`[ROOT-rule:observe:credential-store-contract]`) contains the mechanism name, 600000 rounds, a 16-byte salt, StoredKey and ServerKey with the protocol's separators and standard padded base64, exactly 135 bytes without a line ending. Formatting writes directly into the supplied destination. It does not establish that the supplied keys came from that salt and work factor; the caller composes derivation and formatting under its own custody contract. The primitive-temporary disposition remains (`[ROOT-amend:storage:scram-residue]`) for the host alone.

**Section (Crypto claim area)** · `sec:derivation:crypto` A wrong key role, work factor or verifier framing changes the credential the caller provisions or uses. (`claim:crypto:derivation-matches-independent-vectors`) and (`claim:crypto:derivation-refuses-without-output-or-private-diagnostics`) supply the finite evidence of (`verif:derivation:shared`). Conformance controls compare exact public fixture bytes; robustness controls exercise finite bounds and constant diagnostics. Neither proves entropy, stack erasure or deployment custody.

**Verification (Shared derivation)** · `verif:derivation:shared` (`claim:crypto:derivation-matches-independent-vectors`) compares three distinct public inputs without sorting: the RFC 7677 section 3 example's inputs and two authored inputs at the admitted verifier factor. Intermediate outputs and both complete verifier strings are independently produced by ci/credential_vectors.py using Python hashlib and hmac, calling no workspace code. The RFC publishes the exchange, not these intermediate keys or this verifier formatting; those expectations are the independent producer's. The hash audit regenerates the entire fixture source and refuses any change. (`claim:crypto:derivation-refuses-without-output-or-private-diagnostics`) checks finite work and length refusals before writes and constant input/output/error representations, including one-byte-overlong salted/MAC outputs, client key, stored-key output, verifier salt, stored/server key and verifier destination. Host regression evidence remains owned by its unchanged controls; these claims neither replace them nor admit the later protected consumer.
